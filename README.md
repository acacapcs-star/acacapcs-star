## 齒顎矯正療效預測與軟組織變化量化研究

**中國醫藥大學余建宏醫師研究團隊 × 清華大學 MISLAB（胡敏君教授）**
2026/9 起 · 進行中 · 論文共同掛名
| 成員 | 角色 |
| --- | --- |
| 余建宏教授（中國醫大牙醫系） | 臨床判讀、資料取用 |
| 胡敏君教授（清大資工系／MISLAB） | 模型設計與程式指導 |

這個題目幾乎不需要牙醫背景，可以當成純 CS 的向量問題處理——這是我被邀請加入的理由。

### 專案定義

**資料**：2D 側位頭影 X 光片，每位病人一組術前／術後配對。

**標記點**：藍色為骨骼／解剖點，紅色為軟組織點。由軟體自動標記後人工修正，修正後版本作為 ground truth。

**目標**：從術前影像加術前標記點，預測術後標記點的位置。核心的臨床問題是**門齒移動如何改變軟組織側臉輪廓**。

**臨床價值**：對新病人在療程開始前就能估計術後的側臉外觀。

**資料治理**：資料有 IRB 核准，但限院內使用，所以我到中國醫現場作業。

### 會議一｜2026/9/17 · 專案啟動

胡教授的技術定調（這一句決定了後面所有工作）：

> 先把表示法定義清楚——這個任務本質上是在預測一組 correspondence vector，現有的模型就夠用。

另外兩點建議：既然已經有人工修正過的 ground truth，可以順便 fine-tune 一個更準的標記點偵測模型，減少未來的人工修正量；以及指派我先把 Python／PyTorch 熟起來。

**分工**：Ramish 與我負責實作、余醫師負責臨床判讀、胡教授負責模型與程式指導。先從這個題目開始，順利的話再擴展到其他牙醫 AI 題目。

這一次我沒有帶具體的技術主張，所以也沒有被追問。這個對照在第二次會議之後才看得出意義。

### 會議之間：我交出的東西

**頭影測量模組**——從標記點座標計算 SNA、SNB、ANB、FMA、Wits。過程中記錄了三個會讓結果錯但不會報錯的陷阱：

| 陷阱 | 為什麼會錯 |
| --- | --- |
| ANB 必須用 `SNA - SNB` | 直接取 A–N–B 三點夾角得到的是無正負號的值，Class III 會被讀成 Class II |
| 角度是尺度無關的，距離不是 | 跨機器時角度可以比，mm 的距離沒有校正標記就不能比 |
| 影像的 y 軸向下 | 所有幾何推導要跟著翻，否則上下顛倒 |

**蒙地卡羅誤差傳播**——把每個標記點按自身的 σ 擾動兩千次重算，回報每一項測量的標準差與 95% 區間。

### 會議二｜2026/10/21 · 技術討論

第一次帶具體主張進去的會議。事前把三個問題整理成投影片。

**得到的技術指引**

- **分階段精修可行，但限制在 output 端。** 只用某一個標記點的誤差算 loss 是合法的（loss masking）；但「只更新負責那個點的網路節點」不可行——中間層的特徵是所有輸出共用的分散表徵，那個節點集合並不存在。可以按**結構**凍結（層、backbone），不能按**語意**凍結。
- **Curriculum learning** 是這個想法已被驗證的形式：先整體訓練到粗略正確，再針對需要更準的點細修。
- **離群案例要拿出來看，不是排除。** 模型做最差的那幾個案例是唯一能診斷模型哪裡不行的資料。排除它們只會讓報告的誤差變好看，真實使用時的誤差沒有變。正確做法是找出失敗原因（例如曝光條件差異），再用對應的 data augmentation 處理。
- **資料增強不是把資料變多，是宣告不變性。** 每個 augmentation 都在告訴模型「這個變換不該改變答案」，所以用了一個不成立的不變性，就是在教模型一件假的事。
- **驗證的判準**：假設有一套系統能預測矯正後的標記點，要驗證的是那些預測出的位置是否落在原本設定的目標位置上。

**我自己的方法主張**

> 標記點誤差傳播到角度是不均勻的。在模擬中（假設每點誤差 1.5 px），同樣的點誤差在臂長較長的角度上影響小，在臂長較短的角度上被明顯放大。所以「平均誤差幾 mm」說不出任何一項測量到底能不能用——醫師讀的是角度，需要誤差棒的就是角度。這是模擬下的推論，下一步要用人工修正過的真實標記資料驗證。
>
> 同樣的理由，我主張評估基準應該是 inter-observer variability 而不是絕對誤差。「模型與醫師的差距小於兩位醫師之間的差距」是比「誤差 1.3 mm」強得多的結論。

### 被記錄下來的構想，以及它為什麼不成立

我提了一個模組化架構：模組 A 快速掃出偏離最大的標記點，模組 B 只對那些跑 forward／backward 加 PPO。

胡教授指出兩個問題：

1. 中間的 top-k 選擇**不可微**，梯度到那裡就斷了，模組 A 永遠收不到梯度
2. 更根本的是，選擇標準本身是**循環的**——要先算出誤差才知道哪些點偏離最大，而誤差要等模組 B 跑完才存在

會後查到的解法：

- **Curriculum learning** 把循環拆成前後相接的兩階段，而不是同時互相依賴。第一輪的誤差就是第二階段的選擇依據。
- **Mixture of Experts** 的 router 正是用 softmax 連續權重取代硬選擇來解不可微：取 top-k 之後按權重加權相加，梯度就流得回 router。另外需要 load-balancing loss，否則 router 會塌縮到單一專家（被選得多 → 訓練得好 → 更常被選）。

方向沒錯，缺的是「選擇不要真的斷開」這個技巧。原始構想與它失敗的理由都保留在紀錄裡。

**另一題被判定不在專案範圍內。** 我把一個關於偵測幾何的問題做進投影片，但沒有先檢查它對應到專案目標的哪一塊。釐清之後確認它不是這個專案需要解決的問題。檢查成本是三十秒，我沒做。這之後變成固定流程：任何主張上投影片之前，先問它指到專案目標的哪一層。

### 進行中

- **資料增強方案的提案與審查**——分類哪些變換會破壞標記點標籤的正確性。例如側位片有固定朝向，水平翻轉產生的是解剖上不存在的影像，而且會讓 ANB 的正負反轉；旋轉可用但座標必須同步旋轉；縮放對角度無害，但會讓 mm 的距離失真。提案須經審查確認後才進入訓練。
- **Python／PyTorch**——依會議一的指派進行中
- **與 Ramish 的分工**：他負責整理資料分組與可用的開源標記點偵測程式；我負責測量計算與可靠度分析，並協助他把測量公式整合進標記介面

## 我怎麼練

一開始練 NTUCPC 是為了把語法練熟。家教給我的規定只有一條：不准查 AI——理由是會被 AI 的語法風格帶走，寫出自己不理解的程式碼。

前三分之一的題目，我一題要花 2–3 小時，而且大多是 WA。後來改成先慢下來，按固定順序做：

1. 先寫出大致架構（宣告／輸入／處理／輸出）
2. 註解標出極端值與可能踩的坑
3. 動筆前先分析時間與空間複雜度，避免寫完才發現 TLE

練到三分之一的時候，一題雙重陣列的 DP 讓我第一次做到「3 次以內自我 debug 就 AC」，總共 1.5 小時。之後我開始在每題之前先確認上一次同類型題目 WA 的原因。中段的題目穩定在 45 分鐘到 1.5 小時、3 次以內 AC。

現在的節奏大約是：前 15 分鐘理解題意並找規律、40 分鐘實作（先搭外框再填初始化／計算／轉移）、30 分鐘測試（常態測資與 edge case 分開跑）。

### 三種錯誤，三種處理

| 錯誤 | 我的做法 |
| --- | --- |
| WA | 重新審視邏輯，精簡註解重讀一次 |
| TLE | 換位思考，想辦法把 O(N²) 壓到 O(N log N) 或 O(N) |
| CE | 二分切開排查——把程式碼切一半確認問題在哪一區；檢查大括號是否對稱、分號、以及 float/double 的精度 |

### 一些習慣

- 不用 `<bits/stdc++.h>`，改成 `<iostream>` 加上實際需要的標頭檔。分開寫才知道自己在用什麼
- 大括號一定換行分區塊，不寫一路到底的程式碼
- 變數命名固定：迴圈用 `i, j, k`，累計用 `ans, sum, cnt`

這條「不查 AI」的規則，跟我在專案 README 裡揭露 AI 協助範圍是同一件事的兩面——要能說清楚哪些是自己想出來的，前提是真的有一段時間完全靠自己想。

## 補基礎：從呼叫 API 到知道裡面在做什麼

TankMan 那個專案我用 Stable Baselines3 跑 PPO，拿到了名次。但那是呼叫現成的實作——我不知道 backward 在做什麼、不知道 learning rate 調高為什麼會讓 loss 震盪、也不知道為什麼不能只更新網路的一部分。

2026/9 的專案啟動會議上，胡教授指派我先把 Python／PyTorch 熟起來。我把它當成補那一層，而不是補工具。

**順序**

1. **神經網路的運作**（已完成）
2. **NumPy**（進行中）—— shape、broadcasting、`*` 與 `@` 的差別、`axis`
3. **PyTorch** —— tensor 與 autograd

**檢驗方式是手算。** 設 x = 2、w = 3、b = 1、目標 10、lr = 0.01：

| 步驟 | 結果 |
| --- | --- |
| forward | y = 7，L = (7 − 10)² = 9 |
| backward | ∂L/∂y = −6，∂L/∂w = −12，∂L/∂b = −6 |
| 更新 | w = 3 − 0.01 × (−12) = 3.12 |
| 驗算 | 新的 L = 7.29，確實下降 |
